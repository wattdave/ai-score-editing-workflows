# Architecture

How the code in `src/ai_score_editing/` is laid out and where new things go.
Editor protocols are in [sibelius-protocol.md](sibelius-protocol.md),
[dorico.md](dorico.md) and [musescore.md](musescore.md).

## Layering

Each editor back end is a stack. A layer imports only from layers above it in
this list:

1. **client**: the WebSocket connection (`sibelius/client.py`,
   `dorico/client.py`, `musescore/client.py`). Handshake, token, timeouts.
2. **bridge**: typed calls to the editor's plug-in (`bridge.py` in each
   package; Sibelius's ScoreBridge plug-in is under `sibelius/manuscript/`).
3. **pure score logic**: no I/O (`dorico/score.py`, `musescore/score.py`, and
   everything in `core/`). Locating objects, checking guards, turning a
   validated batch into bridge primitives.
4. **service**: `service.py` in each package. One function per tool (overview,
   structure, query, apply, undo, save, export).
5. **thin front ends**: `cli.py` and `mcp_server.py`. They parse arguments or
   tool parameters, call the service and format the result. No editor logic.

The three back ends expose the same seven tools (`score_overview`,
`score_structure`, `query_score`, `apply_batch`, `undo`, `save_score`,
`export_score`) and the same CLI subcommand and option names. Two tests keep
them aligned: `tests/test_mcp_parity.py` and `tests/test_cli_parity.py`.

## Package map

```
src/ai_score_editing/
  __init__.py      console-script entry points (sibelius-cli)
  cli_common.py    exit codes (0 ok, 1 command failed, 2 connection failed),
                   DEFAULT_LIMIT = 200, export format names, path arguments
  mcp_common.py    Session (lazy connection, error -> ToolError), tool
                   annotations, bar-range and port helpers
  backups.py       one backup policy for all editors
  paths.py         config/cache folders, wire client name
  macos.py         osascript and app-state helpers
  query.py         old import path of the Sibelius query names (see below)
  query_props.json Sibelius property vocabulary (generated by scripts/dev)
  core/            pure helpers, no I/O and no editor imports:
                   units, lyrics, intervals, music, barrange, batch_schema,
                   errors, query, token_store, page_layout, hidden_time
  workflows/       editor-neutral MusicXML/audio pipelines:
                   musicxml_split/ (profiles/), polychoral, rehearsal_mix,
                   mix_proof, musicxml_round, abc_notation
  sibelius/        client, bridge, service, runner, cli (parser + main),
                   commands/, mcp_server, protocol, launcher, batch_ops,
                   query_props, manuscript/ (ScoreBridge.plg), and the
                   Sibelius-only batch helpers
  dorico/          client, bridge (+ bridge.lua), score, service, cli,
                   mcp_server, export, musicxml_read, layout, lyrics_dialog,
                   project_info
  musescore/       client, bridge (+ msbridge.qml.in), score, service, cli,
                   mcp_server, install, instruments, window
```

Shared conventions:

- **Paths.** Config is `$XDG_CONFIG_HOME/ai-score-editing` and cache is
  `$XDG_CACHE_HOME/ai-score-editing` (`~/.config`, `~/.cache` by default). Use
  `paths.config_dir()` and `paths.cache_dir(...)`, never a hard-coded path.
- **Wire client name.** `ai-score-editing` for every editor
  (`paths.WIRE_CLIENT_NAME`); it is what Sibelius Connect and Dorico show in
  their approval prompts.
- **Backups.** Every real `apply` takes a backup first through `backups.py`
  (`--backup-dir`, `$<EDITOR>_BACKUP_DIR`, `$SCORE_BACKUP_DIR`).
- **Errors.** `core/errors.py` has `ScoreEditingError` with `BatchError` and
  `QueryError` below it. Front ends turn them into exit code 1 (CLI) or a
  `ToolError` (MCP).

## Where to add things

**A Sibelius CLI command.** Add or extend a module in
`sibelius/commands/`. A module defines `register(sub)`, which adds the
subparsers and returns `{subcommand name: handler}`; `register_all` discovers
every public module, so there is no list to edit. Handlers take `args` and
return an exit code. Call the bridge and the runner through their modules
(`bridge.call(...)`, `runner.run_op(...)`), not by importing the names, so
tests can patch them. Import from `bridge`, `service`, `runner` and
`commands/_common.py`, never from `cli`, which imports the package. Then add
the command to `.claude/skills/sibelius/references/commands.md`.
Dorico and MuseScore keep their parser and handlers in one `cli.py` each.

**An MCP tool.** Write the service function first, then a thin tool in the
editor's `mcp_server.py` that runs it through `session.run(action, retry=...)`. A tool that
should exist on all three editors must keep the parameter names the others
use, or `tests/test_mcp_parity.py` fails; real differences go in its
`ALLOWED_EXTRA` table.

**A batch operation.** The editor-neutral schema is
`core/batch_schema.py` (`OPERATIONS`, `validate_batch`). Sibelius-only rules,
such as the writable property table that mirrors `BatchWritableTable` in
`ScoreBridge.plg`, live in `sibelius/batch_ops.py`. Then implement the
operation in each editor: the ScoreBridge plug-in (`.plg`) for Sibelius,
`dorico/score.py` plus `bridge.lua`, `musescore/score.py` plus the QML bridge.
An editor that cannot do it refuses it by name (Dorico's `NOT_ON_DORICO` table, for example) and
the editor's page in `docs/` gets a row.

**A query property.** Sibelius: `query_props.json`, regenerated with
`scripts/dev/gen_query_props.py`. The selector engine is `core/query.py`.

**A shared helper.** If it is pure and editor-neutral it goes in `core/`; if
it needs files, audio or a MusicXML pipeline it goes in `workflows/`. `core/`
must not import an editor package.

**A skill.** Edit `.claude/skills/<name>/`, then run
`python3 scripts/sync_skills.py` and `python3 scripts/sync_skills.py --check`.

## Testing seams

- `tests/conftest.py` fails any test that connects to the real Sibelius,
  Dorico or MuseScore port. Mock the bridge instead.
- `tests/fakes.py`: `FakeSibeliusClient` answers bridge methods from a table,
  `bridge_call` and `bridge_apply_batch` patch `sibelius.bridge.call` and the
  batch call, `CliSession` stands in for the MCP session.
- Command handlers are tested by patching `sibelius.runner.<name>` and
  `sibelius.bridge.<name>` (see `tests/test_sibelius_handler_seams.py`).
  This is why handlers call through the module.
- Pure layers (`core/`, `*/score.py`, `workflows/`) are tested without any
  fake. Golden files are under `tests/fixtures/`.
- `tests/test_relative_imports.py` catches imports of moved modules that only
  fail when a command runs. `tests/test_skills_sync.py` checks the skill
  mirrors.

## Backward compatibility

- The old top-level modules are gone (`query`, `batch_ops`, `lyrics`,
  `units`, `intervals`, `music`, `barrange`, the MusicXML tools); the Sibelius
  query names live in `sibelius.query_props`, `QueryError` in `core.errors`, and
  the rest in `core/`, `workflows/` or `sibelius/`. Import them from there.
- The export format `mid` is accepted as `midi` (`cli_common.canonical_format`).
